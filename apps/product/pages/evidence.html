A single New York permit, as it moves through the pipeline. Record values are illustrative; the contracts and code paths are the real ones.

CONTRACT 01 · city_registry.py

The source contract: a DOB row, exactly as published.

Our record is a New York building permit from the Department of Buildings Socrata endpoint. It arrives with the city’s own column names, a watermark column the registry has declared (issuance_date), and an id-key fallback chain (job__ → job_number → id) for resilience against renames.

Nothing is renamed yet. The registry’s job is to declare the feed’s truth — platform, endpoint, watermark, cadence — so every later stage can trust the declaration instead of guessing.

CONTRACT 02 · schemas/models.py

The normalized event: typed, validated, still inspectable.

The producer’s field map resolves the city dialect into a typed permit event. issuance_date becomes occurred_at; the borough name and coordinates survive intact; the raw job__ stays attached as provenance.

Columns the model does not know are preserved on the event for inspection — normalization never deletes context, it adds structure. Malformed rows fail loudly here, at the type boundary, before they can poison any aggregate.

CONTRACT 03 · h3_indexer.py

The spatial address: one event, three canonical cells.

The indexer assigns the event to H3 cells at resolutions 7, 8, and 9 — metro context, submarket grain, and neighborhood cell — then joins the division and submarket names declared in the registry for New York.

After this stage the record can answer a metro-scale question and a block-scale question from the same row, always with one canonical address per resolution.

CONTRACT 04 · lims_calculator.py

The features: decayed, weighted, decomposable.

The calculator folds the event into time-decayed ingredients — CapEx density, permit velocity, 311 shift ratio, license activity — each windowed by its feed’s real cadence, then composes the Leading Indicator Momentum Score for the cell.

The ingredients are stored beside the score. Any LIMS value on the dashboard can be decomposed back into the exact inputs that produced it — that is the point of the composition.

CONTRACT 05 · snapshot_builder.py

The snapshot: versioned, provenance attached.

The builder packages features and model views into a versioned snapshot. The live dashboard reads that artifact; the FastAPI surface (/api/v1/*) serves the same contracts from the spatial store.

Because snapshots are versioned, the edge never silently overwrites its own history — and any number a visitor sees can be traced back through this page to the row that started it.

THE HARD PART

Watermarks, honestly.

Incremental ingestion needs a cursor: “give me everything after this timestamp.” Municipal feeds make that hard in practice — and pretending otherwise is how dashboards end up confidently stale.

Columns drift

A feed’s watermark_col can hold text where a timestamp belongs — “Updated Aug 2023” is a real pattern the NYC deeds and permits feeds produced. A naive cursor stalls forever on the first text value.

Sentinels get excluded

watermarks.py normalizes typed text watermarks and excludes sentinel values, so placeholder rows never masquerade as fresh data. The decision is recorded in ADR 0005.

Staleness is audited

A standing probe compares feed age against declared cadence. When deeds looked stale across six cities, the audit asked: slow source, wrong column, or dead service? The method and findings are public: deeds-watermark-audit.md, nyc-watermark-normalization.md.

Run the same path locally.

With the repository’s local Kafka + PostGIS stack running (setup in the repository README), the exact commands below re-walk this page’s pipeline against live city feeds.
