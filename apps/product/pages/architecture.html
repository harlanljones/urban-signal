THE SPINE

Node by node,
with its contracts.

The machine behind the journey — for the data’s path stage by stage, read /system.

Source producers

One producer per platform family — Socrata, ArcGIS, Carto, CKAN — plus city-specific field maps, so municipal dialects survive to the normalization boundary.

  • Per-feed watermark + id-key declarations
  • Snapshot and year-sliced ingestion modes
  • Scheduler with per-city job names
apps/api/src/producers

City registry

The authoritative contract: canonical city ids, aliases, boundaries, divisions, submarkets, and every dataset spec. If it is not in the registry, it does not exist.

  • CityRegistration: center, bbox, divisions, submarkets
  • DatasetSpec: endpoint, platform, watermark, cadence
  • Readable failures via get_dataset
apps/api/src/spatial/city_registry.py

Kafka backbone

Typed municipal events move through per-family topics; consumers enrich and aggregate without coupling to producers.

  • Permits / 311 / licenses / deeds topics
  • Consumers: spatial enrichment, feature aggregation, PostGIS sync
  • Offsets support replay and reprocessing
apps/api/src/consumers

H3 enrichment

Assigns every event to H3 cells at resolutions 7, 8, and 9, joining division and submarket context from the registry.

  • Multi-resolution hierarchy per event
  • DuckDB out-of-core sink for heavy joins
  • Boundaries and rosters come from the registry
apps/api/src/spatial/h3_indexer.py

Feature aggregation

Time-decayed, interpretable features per cell — the LIMS ingredients — plus catalyst alerts at the public threshold.

  • 180-day half-life CapEx decay
  • Permit velocity, 311 shift dynamics, license activity
  • Catalyst alerts at LIMS ≥ 85.0
apps/api/src/features/lims_calculator.py

Spatial storage

PostGIS is the spatial system of record; object storage holds partitions and model artifacts.

  • Events, features, divisions, snapshots — queryable
  • GiST/BRIN indices on spatial columns
  • Object store for partitions + ONNX artifacts
apps/api/src/storage

Models

Three horizons (6/12/18m) across a spatio-temporal GNN, a cross-network macro model, and a quantile LGBM — walk-forward validated, exported to ONNX.

  • Leakage-controlled splits (validation.py)
  • SHAP attribution feeding the dashboard
  • Calibration before export
apps/api/src/models

Edge delivery

Versioned snapshots land on Workers KV; the dashboard reads precomputed views without hiding their origin.

  • Versioned artifacts with provenance attached
  • FastAPI serves the same contracts live
  • The site’s own facts are registry-projected
apps/api/src/export/snapshot_builder.py

GOVERNANCE, IN PUBLIC

When a city joins,
four gates.

New metros are not added by marketing copy. The repository enforces the sequence — a city that skips a gate does not ship.

01

Declare

A registry entry: city module or inline spec — endpoints, watermark column, id keys, divisions, submarkets.

02

Project

facts:export regenerates the site’s facts and per-city JSON from the registry. Hand-edited coverage cannot drift.

03

Wire

The dashboard map must show the city. The interlock gate (pytest -m interlock) fails any run where a registered city is missing from the map.

04

Publish

Site pages regenerate from the same facts. A city cannot appear here without appearing there — and vice versa.

Read the enforcement. The policy lives in the repository’s agent docs (AGENTS.md), the contract in city_registry.py, and the teeth in test_interlock_gate.py — closure, completeness, containment, registry-export match, and dashboard wiring.
